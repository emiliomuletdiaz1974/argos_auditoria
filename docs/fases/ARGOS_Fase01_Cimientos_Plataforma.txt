0. Método de trabajo y plan maestro de los 100 componentes
Este es el primero de diez documentos técnicos que descomponen ARGOS en sus 100 componentes de ingeniería y los desarrollan uno a uno con la misma disciplina: Análisis (qué problema resuelve el componente, qué requisitos hereda de la especificación de producto y qué alternativas se evaluaron), Diseño (la decisión tomada, sus interfaces y su encaje en las siete capas) y Desarrollo (código completo y ejecutable, con su ruta en el monorepo). El código es la referencia de implementación de la fase F0-F1 del plan de ingeniería: primera versión funcional, con las decisiones de seguridad y soberanía ya incorporadas, sobre la que el equipo itera.
Convenciones de todo el programa: los lenguajes de referencia son Python 3.12 para servicios y conectores, SQL/openCypher para el plano de datos, TypeScript/React para consola, YAML para infraestructura y Bash para operación; todo componente se identifica como ARG-NNN; toda ruta es relativa a la raíz del monorepo argos/; ningún componente escribe jamás en un sistema del cliente; y todo artefacto que cruza una frontera (imagen, bundle, ontología, biblioteca) va firmado.

ARG-001 · Monorepo y convenciones de construcción
ANÁLISIS
ARGOS es un producto de siete capas con decenas de servicios que deben versionarse, probarse y firmarse como una sola imagen de appliance: la release es un todo o no es. Se evaluaron multirepo (aísla equipos pero fragmenta la release y complica la trazabilidad del SBOM único) y monorepo (una revisión = un producto completo, refactorizaciones transversales atómicas, un solo pipeline de firma). Para un equipo de nueve personas que entrega un appliance, el monorepo es la opción con menor fricción y máxima trazabilidad; el riesgo clásico (crecimiento del tiempo de CI) se mitiga con construcción incremental por rutas afectadas.
DISEÑO
Un único repositorio argos/ con cinco raíces: services/ (microservicios Python), connectors/ (SDK y conectores C1), console/ (frontend), platform/ (infraestructura como código del appliance) y library/ (ontología y retos, con su propio ciclo editorial). Un Makefile raíz orquesta todo; cada servicio declara sus dependencias con uv (lockfile reproducible) y se construye como imagen OCI mínima y sin raíz. La convención de identidad: cada componente lleva su ARG-NNN en el pyproject y en la etiqueta OCI, lo que permite reconstruir el SBOM por componente.

argos/Makefile
SHELL := /bin/bash
VERSION := $(shell cat VERSION)
REGISTRY := registry.argos.internal:5000
SERVICES := $(notdir $(wildcard services/*)) $(notdir $(wildcard connectors/*))
 
.PHONY: all build test sbom sign release
 
all: build test sbom sign
 
build:   ## construye todas las imágenes OCI con etiqueta de versión única
for s in $(SERVICES); do \
  d=$$(ls -d services/$$s connectors/$$s 2>/dev/null | head -1); \
  docker build -t $(REGISTRY)/argos-$$s:$(VERSION) \
    --label org.argos.component=$$(cat $$d/COMPONENT) \
    --label org.argos.version=$(VERSION) $$d; \
done
 
test:    ## pruebas unitarias y de contrato de todos los servicios
for s in $(SERVICES); do \
  d=$$(ls -d services/$$s connectors/$$s 2>/dev/null | head -1); \
  (cd $$d && uv run pytest -q --maxfail=1); \
done
 
sbom:    ## SBOM por imagen y SBOM agregado de producto (ARG-087)
mkdir -p dist/sbom
for s in $(SERVICES); do \
  syft $(REGISTRY)/argos-$$s:$(VERSION) -o spdx-json \
    > dist/sbom/argos-$$s-$(VERSION).spdx.json; \
done
 
sign:    ## firma cosign de imágenes y SBOM (clave en Vault, ARG-010)
for s in $(SERVICES); do \
  cosign sign --key hashivault://argos-release \
    $(REGISTRY)/argos-$$s:$(VERSION); \
done
 

ARG-002 · Imagen base del Servidor Cognitivo
ANÁLISIS
El appliance debe arrancar en casa del cliente sin intervención del fabricante y quedar en un estado conocido, reproducible y auditable: sistema mínimo, disco cifrado, k3s listo y ni un paquete de más. Se evaluaron una distribución convencional gestionada con Ansible (deriva de configuración con los años) y una imagen inmutable construida con Packer y configurada por cloud-init en el primer arranque (estado reproducible, actualización por reemplazo transaccional, base del arranque medido de ARG-082). Se elige imagen inmutable sobre Ubuntu Server LTS minimal, que equilibra soporte de drivers NVIDIA y ciclo de parches largo.
DISEÑO
Packer produce la imagen dorada por talla (S/M/L solo difieren en drivers y ajustes de GPU); cloud-init del primer arranque particiona y cifra los volúmenes de datos (el cifrado raíz con TPM llega en ARG-082), fija red y usuario de mantenimiento local sin acceso remoto, e instala el plano k3s desde artefactos incluidos en la propia imagen: el primer arranque funciona sin internet, coherente con P-02 del pliego.

ARG-003 · Orquestación k3s y política de red base
ANÁLISIS
Los servicios necesitan un orquestador con ciclo de vida, reinicios y aislamiento, pero un Kubernetes completo es inasumible de operar dentro de un appliance. k3s aporta la API estándar en un binario único, sin dependencias de nube, con containerd embebido y soporte de registro privado en aislamiento — exactamente el perfil. La alternativa docker-compose se descartó por carecer de políticas de red, gestión declarativa y camino a los clústeres de la talla L (ARG-096).
DISEÑO
Un solo nodo k3s en tallas S/M (la L añade nodos, fase 10) con cuatro namespaces que reproducen las fronteras de capas: argos-core (datos y bus), argos-services (C2-C6), argos-edge (API y consola, lo único expuesto) y argos-ai (vLLM, con acceso a GPU). La política de red parte de denegación total: cada permiso de tráfico es una NetworkPolicy explícita, lo que materializa en el clúster la regla «las capas solo hablan con la inmediata».

# Denegación por defecto en los cuatro namespaces: todo tráfico no
# autorizado expresamente está prohibido (entrada y salida).
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: argos-services }
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
# Permiso mínimo: servicios -> PostgreSQL (5432) y NATS (4222) en core
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: services-to-core, namespace: argos-core }
spec:
  podSelector: { matchLabels: { argos/tier: datastore } }
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector: { matchLabels: { argos/zone: services } }
        - namespaceSelector: { matchLabels: { argos/zone: edge } }
      ports:
        - { protocol: TCP, port: 5432 }
        - { protocol: TCP, port: 4222 }

# Los conectores (services) son los ÚNICOS con salida hacia la red cliente,
# y solo a los CIDR/puertos pactados en implantación (se parchea por cliente).

metadata: { name: connectors-egress-cliente, namespace: argos-services }

  podSelector: { matchLabels: { argos/role: connector } }

  egress:

ARG-004 · PostgreSQL 16 con Apache AGE y pgvector
ANÁLISIS
El producto necesita tres modelos de datos —relacional (campañas, hallazgos, configuración), grafo (inventario, ARG-021) y vectorial (RAG, ARG-053)— y la tentación de tres motores (PostgreSQL + Neo4j + Qdrant) triplicaría la operación, el respaldo y el cifrado dentro del appliance. La especificación ya decidió la consolidación: PostgreSQL 16 con Apache AGE (openCypher sobre el mismo motor transaccional) y pgvector. El coste aceptado es que AGE rinde por debajo de Neo4j en travesías profundas; el objetivo de diseño (<2 s hasta un millón de nodos, ARG-029) se cubre con índices sobre las tablas subyacentes de AGE.
DISEÑO
Imagen propia que apila las dos extensiones sobre la oficial de PostgreSQL; StatefulSet con un réplica en tallas S/M (la HA llega en ARG-095); credenciales servidas desde Vault; y un init-job idempotente que crea extensiones, grafo y esquema núcleo (ARG-005). Ajustes de memoria parametrizados por talla vía ConfigMap.
DESARROLLO

ARG-005 · Esquema de datos núcleo y migraciones
ANÁLISIS
Antes de que existan conectores o retos hace falta el sustrato común que todas las capas comparten: versión de esquema, configuración, sistemas registrados, campañas y —crítico desde el minuto uno— el diario de auditoría encadenado en el que se apoyará la cadena de evidencia (la versión criptográficamente completa llega en ARG-066; aquí nace su tabla con el encadenado de hash ya operativo, porque reescribir un diario a posteriori no es aceptable en un producto de evidencia). Las migraciones se gestionan con ficheros SQL numerados aplicados por un migrador propio minimalista: se evaluó Alembic, pero el appliance exige que la migración sea un artefacto auditable y firmado, no una generación dinámica.
DISEÑO
Esquema argos con las entidades transversales; claves UUID v7 (ordenables por tiempo); todas las tablas con created_at/updated_at; el diario audit_journal es de solo inserción (regla y trigger que prohíben UPDATE/DELETE) y cada entrada incluye el hash de la anterior. El migrador aplica en orden, dentro de transacción, y registra cada migración en el propio diario.
DESARROLLO
services/api/migrations/0001_nucleo.sql
CREATE SCHEMA IF NOT EXISTS argos;
 
CREATE TABLE argos.schema_version (
  version     integer PRIMARY KEY,
  applied_at  timestamptz NOT NULL DEFAULT now(),
  checksum    text NOT NULL
);
 
CREATE TABLE argos.settings (
  key         text PRIMARY KEY,
  value       jsonb NOT NULL,
  updated_at  timestamptz NOT NULL DEFAULT now()

-- Sistemas del cliente registrados para verificación (los puebla C1/C2)
CREATE TABLE argos.systems (
  id           uuid PRIMARY KEY,
  name         text NOT NULL,
  kind         text NOT NULL CHECK (kind IN
               ('rdbms','files','api','directory','clinical','ai','other')),
  environment  text NOT NULL DEFAULT 'produccion',
  owner        text,                       -- dueño de sistema (RACI)
  connection   jsonb NOT NULL,             -- referencia a secreto, no credencial
  read_only_verified_at timestamptz,       -- prueba de no-escritura (P-04)
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now()
);
 
CREATE TABLE argos.campaigns (
  id           uuid PRIMARY KEY,
  name         text NOT NULL,
  status       text NOT NULL DEFAULT 'borrador' CHECK (status IN
               ('borrador','aprobada','en_ejecucion','en_revision','cerrada')),
  scope        jsonb NOT NULL,             -- selectores de sistemas/retos
  windows      jsonb NOT NULL DEFAULT '[]',-- ventanas de ejecución pactadas
  created_by   text NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now(),
  closed_at    timestamptz
);
 
-- Diario de auditoría encadenado: SOLO INSERCIÓN
CREATE TABLE argos.audit_journal (
  seq          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  at           timestamptz NOT NULL DEFAULT now(),
  actor        text NOT NULL,              -- 'system:<svc>' o 'user:<sub>'
  action       text NOT NULL,              -- p.ej. 'query.emit', 'campaign.approve'
  subject      jsonb NOT NULL,
  prev_hash    bytea NOT NULL,
  entry_hash   bytea NOT NULL
);
 
CREATE OR REPLACE FUNCTION argos.journal_forbid() RETURNS trigger AS $$
BEGIN RAISE EXCEPTION 'audit_journal es inmutable'; END $$ LANGUAGE plpgsql;
CREATE TRIGGER journal_no_update BEFORE UPDATE OR DELETE ON argos.audit_journal
  FOR EACH ROW EXECUTE FUNCTION argos.journal_forbid();
 
-- Inserción encadenada: calcula prev/entry hash en el propio motor
CREATE OR REPLACE FUNCTION argos.journal_append(
  p_actor text, p_action text, p_subject jsonb) RETURNS bigint AS $$
DECLARE v_prev bytea; v_seq bigint;
BEGIN
  SELECT entry_hash INTO v_prev FROM argos.audit_journal
   ORDER BY seq DESC LIMIT 1 FOR UPDATE;
  IF v_prev IS NULL THEN v_prev := digest('ARGOS-GENESIS','sha256'); END IF;
  INSERT INTO argos.audit_journal(actor,action,subject,prev_hash,entry_hash)
  VALUES (p_actor,p_action,p_subject,v_prev,
          digest(v_prev || convert_to(p_actor||p_action||p_subject::text,'UTF8'),
                 'sha256'))
  RETURNING seq INTO v_seq;
  RETURN v_seq;
END $$ LANGUAGE plpgsql SECURITY DEFINER;
 
tools/migrate.py — migrador auditable
#!/usr/bin/env python3
"""Migrador ARGOS: aplica SQL numerado, verifica checksum, registra en diario."""
import hashlib, pathlib, sys
import psycopg
 
MIGRATIONS = sorted(pathlib.Path(sys.argv[1]).glob("[0-9]*.sql"))
DSN = sys.argv[2]  # inyectado por el init-job desde Vault
 
def checksum(p: pathlib.Path) -> str:
    return hashlib.sha256(p.read_bytes()).hexdigest()
 
with psycopg.connect(DSN, autocommit=False) as conn, conn.cursor() as cur:
    cur.execute("CREATE SCHEMA IF NOT EXISTS argos")
    cur.execute("""CREATE TABLE IF NOT EXISTS argos.schema_version(
        version int PRIMARY KEY, applied_at timestamptz DEFAULT now(),
        checksum text NOT NULL)""")
    cur.execute("SELECT version, checksum FROM argos.schema_version")
    done = dict(cur.fetchall())
    for m in MIGRATIONS:
        v = int(m.name.split("_")[0])
        cs = checksum(m)
        if v in done:
            assert done[v] == cs, f"¡Migración {v} alterada tras aplicarse!"
            continue
        print(f"aplicando {m.name}")
        cur.execute(m.read_text())
        cur.execute("INSERT INTO argos.schema_version VALUES (%s, now(), %s)", (v, cs))
        cur.execute("SELECT argos.journal_append(%s,%s,%s::jsonb)",
                    ("system:migrator", "schema.migrate",
                     f'{{"version":{v},"checksum":"{cs}"}}'))
    conn.commit()
print("esquema al día")
 

ARG-006 · Bus de eventos NATS JetStream
ANÁLISIS
Las capas cooperan por eventos (un conector descubre una tabla → C2 la ingiere → C3 evalúa aplicabilidad → C4 propone retos) y ese acoplamiento debe ser asíncrono, persistente y reproducible: si un servicio cae, no puede perderse el descubrimiento. Kafka es el estándar pero su coste operativo (JVM, ZooKeeper/KRaft, tuning) es desproporcionado para un appliance; NATS JetStream ofrece persistencia, reentrega y consumidores duraderos en un binario de 20 MB. Los eventos siguen el sobre CloudEvents 1.0 para no inventar un formato propio.
DISEÑO

Sujetos jerárquicos argos.<dominio>.<evento>. Una librería Python común (argos_events) publica y consume con validación de esquema y registro en el diario cuando el evento es relevante para auditoría.

"""argos_events: publicación/consumo CloudEvents sobre JetStream.
Todo servicio usa esta librería; nadie habla NATS a pelo."""
import json, uuid, datetime as dt
import nats
from nats.js.api import ConsumerConfig, DeliverPolicy
 
NATS_URL = "nats://nats.argos-core:4222"
 
def _envelope(source: str, etype: str, data: dict) -> bytes:
    return json.dumps({
        "specversion": "1.0",
        "id": str(uuid.uuid7()),
        "source": f"//argos/{source}",
        "type": f"eu.argos.{etype}",
        "time": dt.datetime.now(dt.UTC).isoformat(),
        "datacontenttype": "application/json",
        "data": data,
    }).encode()
 
class Bus:
    def __init__(self, service: str):
        self.service = service
        self.nc = None; self.js = None
 
    async def connect(self):
        self.nc = await nats.connect(NATS_URL, name=self.service)
        self.js = self.nc.jetstream()
 
    async def publish(self, subject: str, etype: str, data: dict):
        """p.ej. subject='argos.discovery.table_found',
                 etype='discovery.table_found.v1'"""
        ack = await self.js.publish(subject, _envelope(self.service, etype, data))
        return ack.seq
 
    async def subscribe(self, subject: str, durable: str, handler):
        """Consumidor duradero con ack explícito y reentrega."""
        async def _cb(msg):
            try:
                evt = json.loads(msg.data)
                await handler(evt["data"], evt)
                await msg.ack()
            except Exception:
                await msg.nak(delay=30)   # reintento con espera
        await self.js.subscribe(subject, durable=durable, cb=_cb,
            config=ConsumerConfig(deliver_policy=DeliverPolicy.ALL,
                                  max_deliver=5, ack_wait=60))

"""Worker Temporal del dominio de campañas (base para ARG-043..049)."""
import asyncio, datetime as dt
from temporalio import activity, workflow
from temporalio.client import Client
from temporalio.worker import Worker
from temporalio.common import RetryPolicy
 
TEMPORAL = "temporal.argos-core:7233"
TASK_QUEUE = "argos-campaigns"
 
@activity.defn
async def sonda_de_humo(sistema: str) -> dict:
    """Actividad trivial: valida cadena worker->actividad->resultado."""
    return {"sistema": sistema, "ok": True,
            "at": dt.datetime.now(dt.UTC).isoformat()}
 
@workflow.defn
class CampanaHumo:
    @workflow.run
    async def run(self, sistemas: list[str]) -> list[dict]:
        resultados = []
        for s in sistemas:
            r = await workflow.execute_activity(
                sonda_de_humo, s,
                start_to_close_timeout=dt.timedelta(seconds=30),
                retry_policy=RetryPolicy(maximum_attempts=3,
                    backoff_coefficient=2.0))
            resultados.append(r)
        return resultados
 
async def main():
    client = await Client.connect(TEMPORAL, namespace="default")
    worker = Worker(client, task_queue=TASK_QUEUE,
                    workflows=[CampanaHumo], activities=[sonda_de_humo])
    print(f"worker listo en cola {TASK_QUEUE}")
    await worker.run()
 
if __name__ == "__main__":
    asyncio.run(main())

"""Validación de JWT emitidos por Keycloak (realm argos)."""
import time, httpx, jwt
from jwt import PyJWKClient
 
ISSUER = "https://keycloak.argos-core:8443/realms/argos"
_jwks = PyJWKClient(f"{ISSUER}/protocol/openid-connect/certs")
 
class AuthError(Exception): ...
 
def validate(token: str, required_role: str | None = None) -> dict:
    try:
        key = _jwks.get_signing_key_from_jwt(token)
        claims = jwt.decode(token, key.key, algorithms=["RS256"],
                            audience="argos-api", issuer=ISSUER)
    except jwt.PyJWTError as e:
        raise AuthError(f"token inválido: {e}")
    roles = claims.get("realm_access", {}).get("roles", [])
    if required_role and required_role not in roles:
        raise AuthError(f"requiere rol {required_role}")
    return {"sub": claims["sub"], "roles": roles,
            "name": claims.get("preferred_username", "")}
 

ARG-009 · Secretos y PKI interna con Vault
ANÁLISIS
El appliance maneja tres familias de secretos —credenciales de solo lectura hacia sistemas del cliente, contraseñas internas de servicios y las claves de firma— y necesita una CA interna que emita los certificados del mTLS de ARG-083 con rotación automática. Vault resuelve ambas cosas con auditoría propia; el desellado se automatiza contra el TPM del appliance para que un reinicio no exija intervención humana (el sellado por TPM se completa en ARG-082; aquí queda la integración preparada). Alternativa evaluada: cert-manager con CA en secreto plano — rechazada porque deja la clave raíz legible en etcd.
DISEÑO
Vault en argos-core con almacenamiento raft local y dos motores: kv-v2 en /argos (secretos de aplicación, con políticas por servicio: cada servicio lee exclusivamente su rama) y pki con una raíz de 10 años y una intermedia de 1 año que emite certificados de 30 días renovados por los propios pods. Un job de inicialización idempotente configura motores, roles y políticas; las credenciales de conectores hacia sistemas del cliente viven en /argos/connectors/<system-id> y solo el SDK de conectores (ARG-011) tiene política para leerlas.
DESARROLLO
platform/k8s/core/vault/setup.sh (job de inicialización)
#!/usr/bin/env bash
set -euo pipefail
export VAULT_ADDR=https://vault.argos-core:8200
 
# 1) Motores
vault secrets enable -path=argos kv-v2         || true
vault secrets enable pki                        || true
vault secrets tune -max-lease-ttl=87600h pki    # raíz 10 años
 
# 2) CA raíz interna (solo se genera si no existe)
if ! vault read -field=certificate pki/cert/ca >/dev/null 2>&1; then
  vault write -field=certificate pki/root/generate/internal \
    common_name="ARGOS Appliance Root CA" ttl=87600h \
    > /etc/argos/pki/ca.crt
fi
 
# 3) Intermedia para mTLS de servicios (ARG-083 consume el rol)
vault secrets enable -path=pki_int pki          || true
vault secrets tune -max-lease-ttl=8760h pki_int
CSR=$(vault write -field=csr pki_int/intermediate/generate/internal \
      common_name="ARGOS Services CA")
CERT=$(vault write -field=certificate pki/root/sign-intermediate \
      csr="$CSR" format=pem_bundle ttl=8760h)
vault write pki_int/intermediate/set-signed certificate="$CERT"
 
vault write pki_int/roles/argos-svc \
  allowed_domains="argos-core,argos-services,argos-edge,argos-ai" \
  allow_subdomains=true max_ttl=720h ttl=720h
 
# 4) Políticas de mínimo privilegio por servicio
for svc in inventory ontology challenge evidence credentials api; do
cat <<EOF | vault policy write svc-$svc -
path "argos/data/services/$svc/*" { capabilities = ["read"] }
path "pki_int/issue/argos-svc"    { capabilities = ["update"] }
EOF
done
 
# 5) Política EXCLUSIVA de credenciales de conectores (P-04)
cat <<EOF | vault policy write svc-connector-sdk -
path "argos/data/connectors/*" { capabilities = ["read"] }
EOF
 
# 6) Autenticación Kubernetes: cada ServiceAccount -> su política
vault auth enable kubernetes || true
vault write auth/kubernetes/config \
  kubernetes_host=https://kubernetes.default.svc
for svc in inventory ontology challenge evidence credentials api; do
  vault write auth/kubernetes/role/$svc \
    bound_service_account_names=$svc \
    bound_service_account_namespaces=argos-services,argos-edge \
    policies=svc-$svc ttl=1h
done
vault write auth/kubernetes/role/connector-sdk \
  bound_service_account_names=connector-sdk \
  bound_service_account_namespaces=argos-services \
  policies=svc-connector-sdk ttl=1h
echo 'Vault configurado'
 

ARG-010 · Cadena CI/CD con firma de artefactos
ANÁLISIS
La promesa «actualizaciones firmadas, sin túneles» (P-06, P-23) empieza en el pipeline: si la firma se añade al final a mano, tarde o temprano se salta. La cadena debe producir, en cada revisión de main: imágenes reproducibles, pruebas en verde, SBOM por componente y firma cosign con clave custodiada en Vault — y en cada etiqueta de versión, además, el bundle de appliance con su manifiesto firmado que consumirá el actualizador (ARG-086). Se usa un runner autoalojado (el pipeline también debe funcionar sin nubes de CI).
DISEÑO
Pipeline de cuatro etapas (verificar → construir → empaquetar → firmar) definido una sola vez; la clave de release nunca sale de Vault (cosign firma vía transit); el manifiesto de release lista cada imagen con su digest y el hash del SBOM, y es el único fichero que el appliance necesita verificar para confiar en todo lo demás. El gate final reservado (★, la auto-verificación de ARG-100) queda declarado como etapa desde el primer día.
DESARROLLO

tools/make-bundle.sh — manifiesto de release
#!/usr/bin/env bash
# Genera el manifiesto que el actualizador del appliance (ARG-086) verifica.
set -euo pipefail
V=$1; REG=registry.argos.internal:5000
 
imgs=$(docker images --format '{{.Repository}}:{{.Tag}}@{{.Digest}}' \
       | grep "$REG/argos-.*:$V")
 
jq -n --arg v "$V" --arg date "$(date -u +%FT%TZ)" \
  --argjson images "$(printf '%s\n' $imgs | jq -R '{ref:.}' | jq -s)" \
  --argjson sboms  "$(cd dist/sbom && sha256sum *.json | \
                      jq -R 'split("  ")|{sha256:.[0],file:.[1]}' | jq -s)" \
  '{product:"argos", version:$v, built:$date, images:$images, sboms:$sboms}' \
  > dist/release-manifest.json
 
tar -C dist -czf dist/argos-$V.bundle release-manifest.json sbom/
echo "bundle dist/argos-$V.bundle listo"
